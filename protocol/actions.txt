# Action and control ids for Edgepad protocol v1.
#
# RUN_ACTION carries an ACTION id; SET_VALUE and STATE carry a CONTROL id; TEXT carries a TEXT kind. The laptop owns what each
# one does, and ignores any id not listed here: the phone can name an action, never a key or a command.
# PAD_STATE carries a PAD_BUTTON bitmask; TEXT kind 8 carries one PAD_STATUS token. Both are listed here for the same
# reason the actions are: one definition, two codecs, and a test on each side that fails when they drift apart.
# Both test suites check their enums against this file, the same way they check frames.txt.
# HANDSHAKE holds the two values that decide whether a phone can reach a laptop at all.
#
# ACTION 64..95 is a reserved block of 32 macro slots, run as MACRO_BASE + index. The grid ships fifteen
# of them, which is what one TEXT 5 frame can name; the rest of the block is room, not a promise. Only the
# base is named here, because the other ids mean nothing on their own: the laptop's own list decides what
# each slot launches.
# The phone never learns the path, command line or URL behind a slot, only its position and its name.
#
# Format:  KIND id NAME

# the pad only ever needs to be asked for and given back, and an action costs no protocol version: a laptop
# that predates the gamepad drops the id and counts it, and the phone learns as much from the PAD_STATUS it
# never receives. The laptop decides whether it can honour the request and answers with TEXT 8.

# REFRESH_RATE's value is an index into the TEXT 4 list, never a rate in hertz. SET carries value u8 and the
# laptop drops anything above 100, so 120 or 144 could not cross the wire at all; an index is always well
# under 100. It also makes a rate the laptop does not have unrepresentable rather than merely rejected.
CONTROL 4 REFRESH_RATE
# PEN_COLOR's value is an index into the PALETTE rows below: a palette index is the cheapest way to say one of the
# eight stock colours, and an index of 8 or more is dropped and counted. A colour outside the palette is TEXT 17 PEN_RGB.
CONTROL 5 PEN_COLOR
# Where a capture ends up: 0 the laptop keeps it where its own tool saved it, 1 the laptop sends it to the phone
# and deletes its copy only once the phone says it saved it. Any other value is dropped and counted.
CONTROL 6 CAPTURE_TARGET
# Whether this link shares the clipboard: 1 yes, 0 no, phone to laptop. The laptop forgets it when the session ends and
# honours it only while its own clipboard toggle is on (FEATURES "clipboard"). Any other value is dropped and counted.
CONTROL 7 CLIPBOARD
# The stroke width of the next pen-tool strokes, phone to laptop, 1..100. The laptop maps it linearly to a share of the
# screen's height, 0.02% per step: 5 is 0.1% and 100 is 2.0%, and 20 is today's 0.4%, which is what the phone sends as its
# default. 1..4 are accepted and all mean the 0.1% floor. The highlighter keeps its width at 5 times the pen's. 0 or
# more than 100 is dropped and counted. New strokes only; forgotten when the session ends.
CONTROL 8 PEN_WIDTH
# The opacity of the next strokes in percent, phone to laptop, 10..100, 100 by default. The highlighter multiplies its
# own 35% by it. Anything else is dropped and counted. New strokes only; forgotten when the session ends.
CONTROL 9 PEN_OPACITY
# Whether this link forwards the laptop's notifications: 1 yes, 0 no, phone to laptop. Forgotten when the session ends.
# Any other value is dropped and counted. The phone offers it only for a laptop that sent FEATURES "notify".
CONTROL 10 NOTIFY
# Whether this link hears which app is in front (TEXT 21): 1 yes, 0 no, phone to laptop. Forgotten when the session ends.
# Any other value is dropped and counted. The phone offers it only for a laptop that sent FEATURES "foreground".
CONTROL 11 FOREGROUND_WATCH
# A bitmask of what the phone draws right now, phone to laptop: bit0 (1) widgets needing system numbers (CPU, RAM, GPU,
# network), bit1 (2) the System screen, bit2 (4) the weather widget, bit3 (8) an AI widget or the AI screen, bit4 (16) the GitHub
# screen, bit5 (32) the Network page. Values 0..63; larger is dropped and counted. Forgotten when the session ends. It is the ONLY thing that makes the
# laptop sample, read usage files or poll.
CONTROL 12 DASH_WATCH
# Developer mode: 1 on, 0 off, phone to laptop. Any other value is dropped and counted. The laptop keeps it across sessions,
# and the phone shows the laptop's state from FEATURES "developer".
CONTROL 13 DEVELOPER
# Phone to laptop: 1 starts one speed test against Cloudflare (ignored while one runs), 0 cancels the running one. Anything else is
# dropped and counted. The phone offers it only for a laptop that sent FEATURES "netinfo". The answer is TEXT 37.
CONTROL 14 SPEED_TEST

TEXT 0 NOW_PLAYING
TEXT 1 APP
TEXT 2 TIMELINE
TEXT 3 TYPE
# The display's available rates, "/"-separated ASCII such as "60/120/144", in the order CONTROL 4 indexes
# them. The phone labels each step of the refresh dial from this, so its ruler reads 144 HZ and not 2.
TEXT 4 REFRESH_RATES
# The laptop's macro names, "/"-separated such as "Chrome/Spotify/Notes", in the order MACRO_BASE indexes
# them. Empty or never sent means no macros are configured. A blank name keeps its slot: dropping one would
# slide every name after it onto another slot's index, and the phone sends that index.
TEXT 5 MACROS
# One chunk of one macro's icon, laptop to phone: "<slot>/<chunk>/<chunks>/<base64 PNG>". A TEXT payload is
# 255 bytes and an icon is not, so an icon arrives in pieces and the phone joins them; the counts are what
# let it tell a finished icon from a truncated one. Base64 rather than raw bytes because TEXT is defined as
# UTF-8, and widening it would have cost a new frame type and a protocol version with it.
TEXT 6 MACRO_ICON
# The phone asking for the icons, sent when it opens the macro grid. Nothing is pushed unasked: a laptop
# older than this feature drops the request and the phone shows names, and a phone older than it never asks,
# so neither half spends the link on icons the other cannot use. The payload is a decimal side in pixels, and empty means 128.
TEXT 7 WANT_ICONS
# Whether the laptop can offer a virtual controller at all, laptop to phone, as one PAD_STATUS token from the
# fixed set below. Sent in answer to PAD_ATTACH and PAD_DETACH, and once after the handshake so the phone can
# hide the pad rather than offer a button that does nothing.
TEXT 8 PAD_STATUS
# Which optional features this laptop has, laptop to phone, as FEATURE tokens joined by "/" (such as
# "annotate/capture"), sent once after the handshake. A feature missing from the list is off, and a token the
# phone does not know is ignored, so a newer laptop can name more of them than an older phone understands.
TEXT 9 FEATURES
# The laptop's primary display in pixels, "<width>/<height>" such as "1920/1080", laptop to phone, once after
# the handshake and again whenever the display changes. The phone shapes its drawing surface to this ratio so a
# stroke lands where the finger is; PEN itself carries a fraction of the screen and needs no pixels.
TEXT 10 SCREEN_SIZE
# How a SIGN_SAVE ended, laptop to phone, as one SIGN_STATUS token from the set below.
TEXT 11 SIGN_STATUS
# Why a capture the phone asked for did not reach it, laptop to phone, as one CAPTURE_STATUS token from the set below.
TEXT 12 CAPTURE_STATUS
# Which laptop this is, laptop to phone, once after HELLO_ACK: "<32 hex id>/<os>/<name>", os one of the DEVICE_OS tokens
# below. The id is the laptop's stable link id, so the phone can tell one laptop seen over two transports from two.
TEXT 13 DEVICE
# Adding an app as a macro, phone to laptop: "<epoch>.<index>", an index into the list this laptop sent for that epoch.
# The phone never names a path or a command; the laptop keeps the list and an epoch other than its latest is stale.
TEXT 14 APP_ADD
# How an APP_ADD ended, laptop to phone, as one APP_ADD_STATUS token from the set below.
TEXT 15 APP_ADD_STATUS
# Laptop to phone: one character per macro slot, in MACROS order: '-' not trackable (a URL, folder, document or an app the
# laptop cannot see), '0' not running, '1' running, '2' running and in front. Sent when it changes while watched.
TEXT 16 MACRO_OPEN
# A stroke colour of the phone's choosing, phone to laptop: exactly six hex digits, "RRGGBB", either case. It sets the
# colour of new strokes until the next PEN_COLOR or PEN_RGB. Anything else, a "#", a short or long string or a non-hex
# character included, is dropped and counted.
TEXT 17 PEN_RGB
# Laptop to phone: "blocked" while the OS discards synthetic input (Mac without Accessibility trust, Linux without
# write access to /dev/uinput), "ok" otherwise. Sent after HELLO_ACK and on change; never sent by Windows. Never received
# reads as ok.
TEXT 18 INPUT_STATE
# Laptop to phone: a snapshot of the whole battery list, never a delta, "entry|entry|...", entry "kind:level:charging:name"
# split on ":" with limit 4 so the name may contain ":". kind is a BATTERY_KIND token (unknown reads as other), level 0..100
# (clamped), charging 0 or 1. A device with no level, and a laptop with no battery, are omitted. The sender turns control
# characters and "|" in a name into a space, trims, and cuts to 24 code points (never inside a surrogate pair); an empty name
# becomes the kind token. Laptop first, then peripherals in discovery order. Empty means no devices. If the joined UTF-8
# exceeds 255 bytes, whole entries are dropped from the END until it fits (the laptop entry stays). Sent after the
# handshake and when the text differs from the last one sent, polled at most every 60 s.
TEXT 19 BATTERIES
# Laptop to phone: the audio output, "kind/name" split on the first "/" only, kind an OUTPUT_KIND token. The name is the
# device's own for Bluetooth or monitor output ("AirPods Pro") and the endpoint's for built-in ("Speakers"), sanitised as for
# BATTERIES and cut to 40 code points. Empty means no output known. Sent after the handshake and on a default-device change,
# not re-sent when identical.
TEXT 20 OUTPUT
# Laptop to phone: the app in front, "<token>/<name>" split on the first "/". Token 1 to 64 of A-Z a-z 0-9 . _ -  (Windows: the
# lower-cased exe file name; Linux X11: the lower-cased WM_CLASS class; Mac: the bundle id). Name: control characters and "|" turned
# to a space, trimmed, cut to 40 code points. Empty means nothing known. Sent only after CONTROL 11 is 1, on change, never logged.
TEXT 21 FOREGROUND_APP
# Laptop to phone: how many macro slots the laptop keeps, decimal ASCII such as "15". Empty or never sent means the phone's
# own default.
TEXT 22 MACRO_CAP
# Laptop to phone: a CAPTURE_STATE_TOKEN, "idle" or "recording". Best effort: a laptop that cannot tell sends nothing.
TEXT 23 CAPTURE_STATE
# Laptop to phone: the features this laptop cannot offer right now and why, "feature:reason" entries joined by "/", feature a
# FEATURE token and reason an UNAVAILABLE_REASON token. Empty means none. An unknown reason reads as UNSUPPORTED.
TEXT 24 UNAVAILABLE
# Laptop to phone: what END_SLEEP / END_SHUTDOWN armed, as one END_ACTION_TOKEN. Sent on change. An unknown token reads as NONE.
TEXT 25 END_ACTION
# Laptop to phone: the title line of what is playing before it is cleaned for TEXT 0, sent only when it differs from TEXT 0.
TEXT 26 NOW_PLAYING_FULL
# The dashboard kinds, authoritative layout in protocol/dashboard-vectors.txt. Every payload is UTF-8, at most 255 bytes, never
# split inside a character. -1 is an unknown number. Clean(n) turns control characters, tab, "|", "/" and ":" into a space,
# collapses runs, trims and cuts to n code points (never inside a surrogate pair).
# Laptop to phone: "cpu/ram/gpu/vram/down/up/ping/loss/ctemp/gtemp/gpower": percents 0..100, down and up KiB/s, ping ms, loss
# percent, temperatures C, gpower W. Once a second while DASH_WATCH has bit0 or bit1; not re-sent when identical.
TEXT 27 STATS
# Laptop to phone: "cpuName|ramMiB|gpuName|vramMiB|netName", names Clean(30). On watch start and when it changes.
TEXT 28 STATS_INFO
# Laptop to phone: "label:usedPct:totalGiB:freeGiB|...", label Clean(16), at most 6 disks, trailing disks dropped to fit 255.
# Sent while DASH_WATCH has bit1, re-read every 10 s, only when changed.
TEXT 29 DISKS
# Laptop to phone: "agent:state:ctx:title|...", agent an AGENT token, state a SESSION_STATE token, ctx the session's context-window
# fill 0..100 or -1 when unknown, title Clean(24), newest first, at most 8. On change, whatever the watch. Empty means none.
TEXT 30 SESSIONS
# Phone to laptop: exactly "id/a" or "id/d", id 12 lowercase hex. Anything else, or an unknown or answered id, is dropped and counted.
TEXT 31 PERM_ANSWER
# Laptop to phone: "id" of an approval answered elsewhere, timed out, or whose request died. The phone dismisses that sheet.
TEXT 32 PERM_GONE
# Laptop to phone: "agent:window:pct:resetAtMin:measuredAtMin|...". The window is decimal minutes of the limit window (300 is 5 h,
# 10080 a week, 43200 thirty days; any 1..525600), or a LIMIT_WINDOW form: "ctx" for the context window, or "~" and a name
# Clean(16) for a limit with no duration, such as "~spend_limit". pct 0..100 (floats rounded, clamped). The two times are UTC
# minutes since the Unix epoch, -1 unknown. An entry with any other window is dropped. On change; snapshot on DASH_WATCH bit3.
TEXT 33 LIMITS
# Laptop to phone: "agent/measuredAtMin/tokToday/centsToday/tok7d/cents7d/tok30d/cents30d/unpriced|..." integers. 7d and 30d are the
# last 7 and 30 local days, today counted; there is nothing longer, because Claude Code deletes its own history after about 30
# days. Tokens are uncached input plus output; cents are estimates at API list prices; unpriced is 1 when some tokens had no price
# (cents are a lower bound), else 0. On change; snapshot on DASH_WATCH bit3.
TEXT 34 SPEND
# Laptop to phone: "tempTenthsC/wmoCode/city", city Clean(24). Empty means none.
TEXT 35 WEATHER
# Laptop to phone: "kind|band|linkMbps|signalPct|localIp|gateway". kind one of wifi, ethernet, cellular, other, none; band one of 2.4, 5, 6, ?;
# linkMbps and signalPct (0..100) -1 when unknown (Windows never knows the signal); localIp and gateway IPv4 text, empty when none,
# Clean(15). There is NO field for a network name or a hardware address, and none may be added. Sent while DASH_WATCH has bit5,
# once a second at most and only when the text changed.
TEXT 36 NET_INFO
# Laptop to phone: "state|downKbps|upKbps|latencyMs|jitterMs|atUnixMin|bytes". state one of running, done, failed, cancelled, capped;
# the speeds are Kbit/s, the times ms, -1 unknown; atUnixMin is when the test began (UTC minutes since the Unix epoch); bytes is the
# bytes the test actually moved, download plus upload (0 while it starts); the phone shows it as the data used. Sent when a test starts, when it ends, and again to a phone
# that starts watching bit5 while a result is held.
TEXT 37 SPEED_RESULT
# Phone to laptop: exactly "host/listRevision/index". host is a git PROVIDER id (1 to 16 characters), listRevision the revision in the first line
# of the BLOB 7 the phone is showing, index the zero-based position among that blob's P, M, R and A lines (H and N lines are not counted). The
# phone never sends an address. The laptop opens only an https address it fetched itself for that host, that exact revision and that index,
# on the host's own domain, in the default browser. GitHub's page holds one more address after its list lines (index = the number of P, M, R and A
# lines): where the read-only GitHub App is installed, a constant of the laptop. A stale revision, an index out of range, a host that is not connected, an address that
# is not https, or any other shape is dropped and counted.
TEXT 38 GIT_OPEN
