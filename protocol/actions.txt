# Action and control ids for Edgepad protocol v1.
#
# RUN_ACTION carries an ACTION id; SET_VALUE and STATE carry a CONTROL id; TEXT carries a TEXT kind. The laptop owns what each
# one does, and ignores any id not listed here: the phone can name an action, never a key or a command.
# PAD_STATE carries a PAD_BUTTON bitmask; TEXT kind 8 carries one PAD_STATUS token. Both are listed here for the same
# reason the actions are: one definition, two codecs, and a test on each side that fails when they drift apart.
# Both test suites check their enums against this file, the same way they check frames.txt.
# HANDSHAKE holds the two values that decide whether a phone can reach a laptop at all.
#
# ACTION 64..95 is a reserved block of 32 macro slots, run as MACRO_BASE + index. The grid ships fifteen
# of them, which is what one TEXT 5 frame can name; the rest of the block is room, not a promise. Only the
# base is named here, because the other ids mean nothing on their own: the laptop's own list decides what
# each slot launches.
# The phone never learns the path, command line or URL behind a slot, only its position and its name.
#
# Format:  KIND id NAME

# Plug in or unplug the laptop's virtual controller. Actions rather than a frame type of their own, because
# the pad only ever needs to be asked for and given back, and an action costs no protocol version: a laptop
# that predates the gamepad drops the id and counts it, and the phone learns as much from the PAD_STATUS it
# never receives. The laptop decides whether it can honour the request and answers with TEXT 8.
ACTION 35 PAD_ATTACH
ACTION 36 PAD_DETACH
# Annotating the screen and signing, which the laptop draws and the phone only steers. BEGIN shows the laptop's
# overlay and END removes it (and discards the strokes); UNDO and CLEAR edit the strokes; the six TOOL ids pick
# what the next PEN stroke draws. SIGN_BEGIN opens a signing pad that shows nothing on the laptop and accepts
# only the pen tool, and SIGN_SAVE asks the laptop to export what was drawn and answer with SIGN_STATUS. Actions
# because the phone only asks; a laptop too old to know the ids drops and counts them.

# Screen capture, which is the laptop's own tool: a region (a drag), the whole screen, and a recording. Actions
# because the phone only asks; what each one presses is the laptop's business, and a laptop too old to know
# them drops and counts the id. The phone shows the buttons only for a laptop that sent FEATURES "capture".
ACTION 52 CAPTURE_REGION
ACTION 53 CAPTURE_SCREEN
ACTION 54 CAPTURE_RECORD
# The phone left its capture screen: the laptop dismisses a capture overlay it opened, only if one may still be open.
ACTION 55 CAPTURE_CANCEL
# Adding a macro from the phone. APPS_LIST asks the laptop to list the apps it could add (names as a BLOB kind 2, then
# one BLOB kind 3 icon each); APPS_CANCEL stops that list and its icons. The phone shows the buttons only for a laptop
# that sent FEATURES "apps".
ACTION 56 APPS_LIST
ACTION 57 APPS_CANCEL
# The first of the 32 macro slots; slot n is MACRO_BASE + n. A laptop older than the macros feature drops an
# unknown action id rather than erroring, which is why the block needs no new frame type and no version bump.
ACTION 64 MACRO_BASE

CONTROL 3 MEDIA_POSITION
# REFRESH_RATE's value is an index into the TEXT 4 list, never a rate in hertz. SET carries value u8 and the
# laptop drops anything above 100, so 120 or 144 could not cross the wire at all; an index is always well
# under 100. It also makes a rate the laptop does not have unrepresentable rather than merely rejected.
CONTROL 4 REFRESH_RATE
# PEN_COLOR's value is an index into the PALETTE rows below, never a colour: the phone cannot name an RGB the
# laptop did not agree to, and an index of 8 or more is dropped and counted.
CONTROL 5 PEN_COLOR
# Where a capture ends up: 0 the laptop keeps it where its own tool saved it, 1 the laptop sends it to the phone
# and deletes its copy only once the phone says it saved it. Any other value is dropped and counted.
CONTROL 6 CAPTURE_TARGET
# Whether this link shares the clipboard: 1 yes, 0 no, phone to laptop. The laptop forgets it when the session ends and
# honours it only while its own clipboard toggle is on (FEATURES "clipboard"). Any other value is dropped and counted.
CONTROL 7 CLIPBOARD

TEXT 0 NOW_PLAYING
TEXT 1 APP
TEXT 2 TIMELINE
TEXT 3 TYPE
# The display's available rates, "/"-separated ASCII such as "60/120/144", in the order CONTROL 4 indexes
# them. The phone labels each step of the refresh dial from this, so its ruler reads 144 HZ and not 2.
TEXT 4 REFRESH_RATES
# The laptop's macro names, "/"-separated such as "Chrome/Spotify/Notes", in the order MACRO_BASE indexes
# them. Empty or never sent means no macros are configured. A blank name keeps its slot: dropping one would
# slide every name after it onto another slot's index, and the phone sends that index.
TEXT 5 MACROS
# One chunk of one macro's icon, laptop to phone: "<slot>/<chunk>/<chunks>/<base64 PNG>". A TEXT payload is
# 255 bytes and an icon is not, so an icon arrives in pieces and the phone joins them; the counts are what
# let it tell a finished icon from a truncated one. Base64 rather than raw bytes because TEXT is defined as
# UTF-8, and widening it would have cost a new frame type and a protocol version with it.
TEXT 6 MACRO_ICON
# The phone asking for the icons, sent when it opens the macro grid. Nothing is pushed unasked: a laptop
# older than this feature drops the request and the phone shows names, and a phone older than it never asks,
# so neither half spends the link on icons the other cannot use. The payload is empty.
TEXT 7 WANT_ICONS
# Whether the laptop can offer a virtual controller at all, laptop to phone, as one PAD_STATUS token from the
# fixed set below. Sent in answer to PAD_ATTACH and PAD_DETACH, and once after the handshake so the phone can
# hide the pad rather than offer a button that does nothing.
TEXT 8 PAD_STATUS
# Which optional features this laptop has, laptop to phone, as FEATURE tokens joined by "/" (such as
# "annotate/capture"), sent once after the handshake. A feature missing from the list is off, and a token the
# phone does not know is ignored, so a newer laptop can name more of them than an older phone understands.
TEXT 9 FEATURES
# The laptop's primary display in pixels, "<width>/<height>" such as "1920/1080", laptop to phone, once after
# the handshake and again whenever the display changes. The phone shapes its drawing surface to this ratio so a
# stroke lands where the finger is; PEN itself carries a fraction of the screen and needs no pixels.
TEXT 10 SCREEN_SIZE
# How a SIGN_SAVE ended, laptop to phone, as one SIGN_STATUS token from the set below.
TEXT 11 SIGN_STATUS
# Why a capture the phone asked for did not reach it, laptop to phone, as one CAPTURE_STATUS token from the set below.
TEXT 12 CAPTURE_STATUS
# Which laptop this is, laptop to phone, once after HELLO_ACK: "<32 hex id>/<os>/<name>", os one of the DEVICE_OS tokens
# below. The id is the laptop's stable link id, so the phone can tell one laptop seen over two transports from two.
TEXT 13 DEVICE
# Adding an app as a macro, phone to laptop: "<epoch>.<index>", an index into the list this laptop sent for that epoch.
# The phone never names a path or a command; the laptop keeps the list and an epoch other than its latest is stale.
TEXT 14 APP_ADD
# How an APP_ADD ended, laptop to phone, as one APP_ADD_STATUS token from the set below.
TEXT 15 APP_ADD_STATUS

# The bitmask a PAD_STATE frame's "buttons" field carries. These are XInput's own wButtons values, unchanged
# and in decimal, because the laptop copies the field straight into an XINPUT_GAMEPAD rather than remapping
# it: a table of its own here would be a second definition to keep in step with Microsoft's. 0x0800, between
# GUIDE and A, is unused by XInput and stays unused here. NONE is the empty mask, nothing held, which is a
# real state of the field rather than padding: it is what a PAD_STATE carries the moment a button comes up.

# The whole vocabulary of TEXT kind 8, as "<token on the wire> <the name both apps call it>". A token, not a
# sentence, because the phone branches on it: READY is the only one that leaves the pad usable, and the other
# two are the two different things it has to tell the user when it falls back to the keyboard. Prose here
# would mean the phone matching on the laptop's wording, which is how a message becomes unchangeable.
# An unknown token is treated as NO_DRIVER: the pad is not usable and the phone cannot say why.
PAD_STATUS ready READY
PAD_STATUS no-driver NO_DRIVER
PAD_STATUS attach-failed ATTACH_FAILED

# The whole vocabulary of TEXT kind 9, as "<token on the wire> <the name both apps call it>". Tokens for the
# reason PAD_STATUS is: the phone branches on them, so prose would make the laptop's wording unchangeable.
FEATURE annotate ANNOTATE
FEATURE capture CAPTURE
# Named only while the laptop's own clipboard toggle is on.
FEATURE clipboard CLIPBOARD
# The laptop can list its apps for the phone to add as macros.
FEATURE apps APPS

# The whole vocabulary of TEXT kind 13's second field, as "<token on the wire> <the name both apps call it>". The phone
# uses it only to word hints that differ by OS; an unknown token reads as no OS known.
DEVICE_OS windows WINDOWS
DEVICE_OS linux LINUX
DEVICE_OS macos MACOS

# What a FILE_BEGIN may carry, as "<id> <NAME> <MIME type> <extension>". An id, never a MIME string of the laptop's
# choosing: the phone writes only these types, and an id it does not know is refused. The laptop sends only a file
# whose extension is in this list.
FILE_TYPE 0 PNG image/png png
FILE_TYPE 1 JPEG image/jpeg jpg
FILE_TYPE 2 MP4 video/mp4 mp4

FILE_TYPE 4 WEBM video/webm webm

# The largest file of each kind that crosses the link, in bytes, as "<bytes> <KIND>": an image type is IMAGE and a
# video type VIDEO. The laptop keeps a bigger one and says too-large; the phone refuses a bigger FILE_BEGIN.
