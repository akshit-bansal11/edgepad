# Action and control ids for Edgepad protocol v1.
#
# RUN_ACTION carries an ACTION id; SET_VALUE and STATE carry a CONTROL id; TEXT carries a TEXT kind. The laptop owns what each
# one does, and ignores any id not listed here: the phone can name an action, never a key or a command.
# PAD_STATE carries a PAD_BUTTON bitmask; TEXT kind 8 carries one PAD_STATUS token. Both are listed here for the same
# reason the actions are: one definition, two codecs, and a test on each side that fails when they drift apart.
# Both test suites check their enums against this file, the same way they check frames.txt.
# HANDSHAKE holds the two values that decide whether a phone can reach a laptop at all.
#
# ACTION 64..95 is a reserved block of 32 macro slots, run as MACRO_BASE + index. The grid ships fifteen
# of them, which is what one TEXT 5 frame can name; the rest of the block is room, not a promise. Only the
# base is named here, because the other ids mean nothing on their own: the laptop's own list decides what
# each slot launches.
# The phone never learns the path, command line or URL behind a slot, only its position and its name.
#
# Format:  KIND id NAME

# Plug in or unplug the laptop's virtual controller. Actions rather than a frame type of their own, because
# the pad only ever needs to be asked for and given back, and an action costs no protocol version: a laptop
# that predates the gamepad drops the id and counts it, and the phone learns as much from the PAD_STATUS it
# never receives. The laptop decides whether it can honour the request and answers with TEXT 8.
ACTION 35 PAD_ATTACH
ACTION 36 PAD_DETACH
# The first of the 32 macro slots; slot n is MACRO_BASE + n. A laptop older than the macros feature drops an
# unknown action id rather than erroring, which is why the block needs no new frame type and no version bump.
ACTION 64 MACRO_BASE

CONTROL 0 VOLUME
CONTROL 1 BRIGHTNESS
CONTROL 2 MIC_LEVEL
CONTROL 3 MEDIA_POSITION
# REFRESH_RATE's value is an index into the TEXT 4 list, never a rate in hertz. SET carries value u8 and the
# laptop drops anything above 100, so 120 or 144 could not cross the wire at all; an index is always well
# under 100. It also makes a rate the laptop does not have unrepresentable rather than merely rejected.
CONTROL 4 REFRESH_RATE

TEXT 0 NOW_PLAYING
TEXT 1 APP
TEXT 2 TIMELINE
TEXT 3 TYPE
# The display's available rates, "/"-separated ASCII such as "60/120/144", in the order CONTROL 4 indexes
# them. The phone labels each step of the refresh dial from this, so its ruler reads 144 HZ and not 2.
TEXT 4 REFRESH_RATES
# The laptop's macro names, "/"-separated such as "Chrome/Spotify/Notes", in the order MACRO_BASE indexes
# them. Empty or never sent means no macros are configured. A blank name keeps its slot: dropping one would
# slide every name after it onto another slot's index, and the phone sends that index.
TEXT 5 MACROS
# One chunk of one macro's icon, laptop to phone: "<slot>/<chunk>/<chunks>/<base64 PNG>". A TEXT payload is
# 255 bytes and an icon is not, so an icon arrives in pieces and the phone joins them; the counts are what
# let it tell a finished icon from a truncated one. Base64 rather than raw bytes because TEXT is defined as
# UTF-8, and widening it would have cost a new frame type and a protocol version with it.
TEXT 6 MACRO_ICON
# The phone asking for the icons, sent when it opens the macro grid. Nothing is pushed unasked: a laptop
# older than this feature drops the request and the phone shows names, and a phone older than it never asks,
# so neither half spends the link on icons the other cannot use. The payload is empty.
TEXT 7 WANT_ICONS
# Whether the laptop can offer a virtual controller at all, laptop to phone, as one PAD_STATUS token from the
# fixed set below. Sent in answer to PAD_ATTACH and PAD_DETACH, and once after the handshake so the phone can
# hide the pad rather than offer a button that does nothing.
TEXT 8 PAD_STATUS

# The bitmask a PAD_STATE frame's "buttons" field carries. These are XInput's own wButtons values, unchanged
# and in decimal, because the laptop copies the field straight into an XINPUT_GAMEPAD rather than remapping
# it: a table of its own here would be a second definition to keep in step with Microsoft's. 0x0800, between
# GUIDE and A, is unused by XInput and stays unused here. NONE is the empty mask, nothing held, which is a
# real state of the field rather than padding: it is what a PAD_STATE carries the moment a button comes up.
PAD_BUTTON 0 NONE
PAD_BUTTON 1 DPAD_UP
PAD_BUTTON 2 DPAD_DOWN
PAD_BUTTON 4 DPAD_LEFT
PAD_BUTTON 8 DPAD_RIGHT
PAD_BUTTON 16 START
PAD_BUTTON 32 BACK
PAD_BUTTON 64 LEFT_THUMB
PAD_BUTTON 128 RIGHT_THUMB
PAD_BUTTON 256 LEFT_SHOULDER
PAD_BUTTON 512 RIGHT_SHOULDER
PAD_BUTTON 1024 GUIDE
PAD_BUTTON 4096 A
PAD_BUTTON 8192 B
PAD_BUTTON 16384 X
PAD_BUTTON 32768 Y

# The whole vocabulary of TEXT kind 8, as "<token on the wire> <the name both apps call it>". A token, not a
# sentence, because the phone branches on it: READY is the only one that leaves the pad usable, and the other
# two are the two different things it has to tell the user when it falls back to the keyboard. Prose here
# would mean the phone matching on the laptop's wording, which is how a message becomes unchangeable.
# An unknown token is treated as NO_DRIVER: the pad is not usable and the phone cannot say why.
PAD_STATUS ready READY
PAD_STATUS no-driver NO_DRIVER
PAD_STATUS attach-failed ATTACH_FAILED
