# Architecture

Edgepad is one product in four programs: one phone app and three laptop apps, for Windows, macOS and Linux. The two .NET laptop apps share one library, the shared core, and the Mac app is Swift and keeps its own copy of the same logic. This page is the map of them and of the seams between them: what runs where, on which thread, what trusts what, and why. The diagram shows the Windows laptop; the Mac and Linux apps are described below.

```
Android phone                                   Windows laptop
--------------------------------------          ----------------------------------------
MainActivity                                    Edgepad.exe (WinForms tray, one instance)
  screens: guide, devices, settings pages,      TrayContext: menu, status, run at login
           layouts, keyboard, gamepad,          RfcommServer: advertises the service
           connection lost                        Session (one per phone, own thread)
  ControlSurface (one View, all drawn)              FrameCodec -> Dispatcher
    TrackpadRecognizer -> frames                      InputInjector (SendInput)
    Shapes -> action, macro or pad mode               VirtualPad (ViGEmBus)
    Dial x4 -> SET / ACTION frames                    AudioEndpoint (Core Audio)
    keyboard -> TEXT frames                           BrightnessControl (WMI)
    gamepad -> PAD_STATE frames                       MediaSessions (system media controls)
  LaptopLink: RFCOMM socket                           STATE / TEXT / PONG back to the phone
    reader thread, writer thread,   <-- RFCOMM -->
    coalescing outbox
  LaptopState: the laptop's last report
```

The diagram shows the default Bluetooth link. Wi-Fi and USB connections, optional and off until the laptop's owner turns them on, carry the same frames over TCP; see [PROTOCOL.md](PROTOCOL.md).

## The split

The phone recognises; the laptop executes. Every touch is turned into a semantic frame on the phone (pointer moved, button pressed, scroll, zoom, run action 3, set control 0 to 55, type "hi", here is the whole controller) and the laptop carries it out with the Windows APIs. The laptop owns the table of what each action id does, which is what lets the two halves be versioned apart and an id one of them has never heard of be dropped and counted rather than misexecuted.

That table is a versioning seam and not a containment boundary, and should not be read as one: KEY carries a raw Windows virtual-key code and TEXT kind 3 carries arbitrary characters, both of which the laptop injects directly, because that is exactly what the phone's keyboard screen is. A paired phone is a trusted input device, and the trust boundary is the pairing plus trust on first use described under **Trust** below. [SECURITY.md](../SECURITY.md) says the same at more length.

The laptop also reports: a snapshot of volume, mute, microphone and brightness after the handshake, then every change as it happens, plus what is playing and whether it can offer a virtual controller. The phone keeps the last report in `LaptopState`, which outlives the control surface, so a surface rebuilt after a rotation or a theme change starts from real values and never shows 0 for a level it has not heard. The pad's status is kept there for the same reason and one more: the laptop volunteers it once after the handshake and otherwise only answers a request, so a rotation that rebuilt the gamepad screen would lose the only answer it had been given.

## The laptop apps and the shared core

```
shared/Edgepad.Core (net10.0, every type internal)
  Protocol   Frame, FrameCodec, Ids, ProtocolConstants
  Net        FrameStream, Handshake
  Trust      TrustStore, PinStore, PinGate, PrivateStorage
  Dispatch   Dispatcher (routing), IPlatform (the per-OS action table)
  Macros     MacroStore, IMacroLauncher, IMacroRunner
  Annotation StrokeBoard      Controls  Subscription
  Updates    UpdateCheck      Log
        ^                         ^
windows/src/Edgepad         linux/src/Edgepad.Linux          macos/ (Swift, own core)
 WinForms tray, WinRT        Avalonia tray, BlueZ over        AppKit menu bar,
 RFCOMM, SendInput,          D-Bus, uinput, logind,           IOBluetooth, CGEvent,
 ViGEmBus, Core Audio, WMI   wpctl/pactl, MPRIS              Core Audio, DisplayServices
```

What is in the core is what has the same shape on every OS and can run on a CI runner with nothing attached: the codec and the stream that reassembles frames, the handshake in its one safe order, the trust file and the PIN store, the dispatcher's routing and drop-and-count rules, the macro list and the stroke model that annotation and signing draw into. The dispatcher asks `IPlatform` to do the actual thing (press a key, set a level, plug in a pad), so what an action id does on an OS is that OS's one table and the routing around it is written once.

What stays in each app is whatever touches the OS: on Windows the WinRT Bluetooth stack, `SendInput`, Core Audio and WMI, ViGEmBus and the system media controls, which are COM and WinRT objects with their own apartments and threads; on Linux BlueZ, uinput, logind and the desktop's own tools; on a Mac IOBluetooth, CGEvent and AppKit. These have no shared shape (a COM audio endpoint and a `wpctl` child process have nothing in common but the word volume), and forcing an interface over them would be a second copy of each API to keep true. So the line is drawn where the behaviour is the same, not where the topic is.

Every core type is `internal`, with `InternalsVisibleTo` naming the two apps and the three test projects, so the library is not a public surface anyone could depend on and the apps and tests are the only callers. The Mac app cannot reference .NET, so `macos/Sources/EdgepadCore` is a Swift rewrite of the same pieces, and the two golden fixtures in `protocol/` are what keep it honest (see **What the tests cover**).

## Transport

Bluetooth Classic RFCOMM is the default transport: one service UUID both sides know, with the socket bound at `BluetoothEncryptionWithAuthentication`. That means only a device already paired with the laptop can connect, the stream is encrypted by the link layer, and there is no discovery or server. Wi-Fi and USB connections are an optional second transport on Windows, Linux and the Mac, off until the owner turns it on; see [PROTOCOL.md](PROTOCOL.md). On a Mac the same RFCOMM service is offered through IOBluetooth, which has no equivalent of that protection level; see **The Mac app** below for what stands in for it. On Linux BlueZ's `RegisterProfile` is called with `RequireAuthentication`, the analogue of the Windows protection level; see **The Linux app**.

Rejected on the way here: BLE GATT (Windows as a GATT server is unreliable across adapters, and GATT is datagram-shaped where an ordered stream is wanted), Wi-Fi as the default (it needs a shared network and a discovery step, so it is an optional extra instead), and making the phone a Bluetooth HID touchpad (Windows only runs its multi-finger gestures for certified Precision Touchpad hardware, so the gestures would have to be emulated anyway).

## Frames

`docs/PROTOCOL.md` has the byte layout. The shape that matters here: one type byte, then a payload whose length is fixed by the type, except TEXT, which carries its own length. Frames are 2 to 258 bytes. All three codecs (Kotlin, the shared C# core and Swift) are held to the same golden fixture file by their test suites, so the apps cannot drift apart without a test failing on one side.

The version is 5, moved from 4 by 4.0.0 for the PIN_REQUEST and PIN_ANSWER frames (the gate they serve is in `docs/PROTOCOL.md`) and the PEN frame. It was 4, moved from 3 by 3.0.0 to make room for PAD_STATE. It carries the whole controller — buttons, both triggers, both sticks — in one payload laid out byte for byte like Windows' own `XINPUT_GAMEPAD`, so the laptop copies the fields onto a report rather than translating them, and there is no range or button order of ours to hold against Microsoft's. Only a new frame type forces a version, and the version moves only in a major release, which is why one frame's arrival is the whole of the difference between 3 and 4. The handshake refuses a mismatch, so both halves of a release are installed together or neither connects.

Latency is the design priority after correctness. The phone dispatches touch unbuffered and feeds every historical sample through; the writer thread sends everything queued in one write; and a backlog of MOVE, SCROLL and ZOOM frames still waiting in the outbox is summed into one before it goes out, so a slow link catches up in a single packet instead of replaying every sample it missed. A backlog of SET or PAD_STATE frames collapses to the newest instead of summing, because each of those is a snapshot rather than a change and the ones before it describe a moment that has passed. KEY and POINTER_BUTTON are never collapsed at all: they are edges, and dropping a release would leave the key or the button held down on the laptop with nothing left to lift it. The laptop injects input on the reading thread itself: there is no queue between the socket and `SendInput`.

## Threads

**Phone.** `LaptopLink.open` blocks for the life of the connection on its own thread and reads there. A second thread drains the outbox and writes. `send` never blocks, so touch handling never waits on the link. Every callback into the activity is posted to the main thread. The link is kept across configuration changes through `onRetainNonConfigurationInstance` and its listener swapped to the new activity. When the app leaves the foreground, anything held down is released at once, but the link itself is kept for 30 seconds (or, with Stay connected on, for as long as its notification stands, which has a Disconnect button), so picking a background image, a trip to Bluetooth settings or the screen going off does not drop it; it closes if the app is not back by then, and at once when the app is finished. Off Devices and Settings, where the round-trip readout is, the link is pinged every 5 seconds rather than every half second.

**Laptop.** `RfcommServer` accepts on WinRT's thread and hands each socket to a `Session` running on a dedicated above-normal-priority thread, where the read loop turns frames straight into input. A new connection starts as a candidate, tracked so that Forget and quitting can end it, but it does not displace the connected phone. Only once its handshake and trust check have succeeded, just before HELLO_ACK, does the server make it current and end the previous session. That order is deliberate: the same phone replacing its own stale link after a drop (it reconnects before the laptop's old socket has noticed it is dead) must win, a trusted phone may take over from another, and an untrusted phone that merely connects must not drop the connected one. A phone that was replaced by a different one is refused for 30 seconds, which outlasts its own ten automatic retries two seconds apart, so the two phones do not take the laptop back and forth; after that it can reconnect with Retry. If starting Bluetooth fails, `RfcommServer` tries again every 30 seconds until it works, logging each distinct failure once, and it restarts itself when the PC resumes from sleep and when the Bluetooth radio is turned back on, subscribing to the radio again after every successful start. A restart does not end a live session. Audio-change notifications arrive on COM threads and brightness events on a WMI thread; `Session.Send` is locked so they interleave safely with the read loop's PONGs. Brightness writes go to their own thread with latest-value-wins, because a WMI call is far slower than a frame and queueing would make a dial drag lag further behind the finger the longer it moved. Media state is read from Windows' system media transport controls and extrapolated once a second while playing.

`VirtualPad` belongs to the session thread too, and is written the way `InputInjector` is: no exception leaves it. ViGEmBus is a separate install this laptop may not have, may have removed, or may have at a version the client cannot speak to, and all three are ordinary states rather than faults — every entry point answers with a `PAD_STATUS` token instead, which is what that token exists for. A tray app has no dialog to show a crash in, and an escape from the session thread would take the link with it and everything the phone was holding down. Failures are caught by namespace rather than by a list of types, because the library's exceptions derive straight from `Exception` with no common base and the one a list missed would be the crash the class exists to prevent. The driver is looked for once per connection and the answer kept, so a phone may press attach as often as it likes; the cost is that a ViGEmBus installed mid-session is not noticed until the phone reconnects.

**Held input.** The app switcher works by holding Alt across frames. `InputInjector` remembers everything it holds down — including the raw virtual-key codes the on-screen keyboard and the gamepad send, which it did not until 3.0.0 — and releases it all when a session ends, so a link dropped mid-gesture can never leave Alt, a mouse button or a key stuck on the laptop. The virtual controller is unplugged on the same path in the session's `finally`, and for the same reason: a phone that disappears mid-game must not leave a pad plugged into Windows with a stick still pushed forward and nothing alive to centre it.

## Trust

Two layers. Pairing, enforced by the socket's protection level: unpaired devices cannot connect at all. Trust on first use, enforced by `TrustStore`: any paired phone that is not yet trusted makes the tray ask **Trust this phone?** once it completes the handshake, and HELLO_ACK is withheld until the answer. **Trust** appends its Bluetooth address to `%APPDATA%\Edgepad\trusted-phone.txt` on Windows, one address per line, so any number of phones can be trusted; a file from an older release holding one address is read as a list of one. **Don't trust**, or no answer within 60 s, closes the connection. A connection arriving while the question is open is refused without a second question and without disturbing the phone being asked about, and a phone the owner said no to is not asked about again for 30 seconds. A phone already trusted is admitted without a question. The tray menu's **Forget trusted phones** hangs up on the connected phone and refuses every connection while it asks, since the phones are still trusted then and would reconnect under the question; a yes clears every trusted phone and keeps refusing for 30 seconds, anything else takes connections again; it stays available when the trust file exists but cannot be read, which is the state that refuses every phone. A Forget that happens while a question is open wins: `TrustStore` counts forgets, and a yes that arrives after one saves nothing. Every phone you trust has full keyboard-level control, and a trusted phone that is connected can answer the question about another phone with its keyboard, which gives it nothing it did not already have.

On a Mac the first layer is done by the app, and it is the Mac's own check, not something the phone supplies: it refuses a connecting device that macOS does not report as paired, requires `requestAuthentication()` to succeed, and logs how long that took. A paired address is only an entry on a list, and trust is keyed on the address too, so the address alone would let a device that copied a trusted phone's address in; authentication needs the key made at pairing. The laptop-side gates are therefore that the phone is paired, that the link authenticates (the Mac's `requestAuthentication()`, or on Windows the socket's `BluetoothEncryptionWithAuthentication` protection level), and the owner's yes. The socket that Android requests is not one of them, since an attacker chooses their own socket. The second layer is the same, quiet periods included, with the question asked in a dialog and the addresses kept in `~/Library/Application Support/Edgepad/trusted-phone.txt`, created readable by its owner only. On Linux the file is `$XDG_CONFIG_HOME/edgepad/trusted-phone.txt` (normally `~/.config/edgepad`), and the shared core creates its folder 0700 and writes the file 0600, as the Mac does; on Windows the per-user `%APPDATA%` folder is already private.

The handshake also carries a protocol version. A mismatch is refused with the laptop's version in the reply, so the phone can say which side needs updating instead of misreading frames.

Windows itself adds a boundary the app cannot cross: `SendInput` is silently refused when an elevated window or the secure desktop has focus. The laptop counts those refusals and logs them once per session.

## The PIN gate and holds

Protocol 5 adds an optional second step after trust, set from the tray's **Security…** window. Level 1 (the default) is trust only and sends no PIN frame at all. Level 2 asks each phone for a six-digit PIN once, and level 3 on every connection. The order, written once in `Net/Handshake.cs` and shared by the Windows and Linux apps (the Mac's `Session` follows it in Swift), is:

1. HELLO and the version check. A mismatch is answered with the laptop's version and closed.
2. The locked-out check. A phone whose address has used up its tries gets `PIN_REQUEST(0, secondsLeft)` and is closed before anyone is asked anything, so guessing cannot also keep the trust question on the owner's screen.
3. The trust question, unchanged.
4. The PIN gate (`PinGate`), only where the level requires it: `PIN_REQUEST(attemptsLeft, 0)`, then a minute for `PIN_ANSWER`, repeated until it is right, the phone is locked out or the answer cannot be judged.
5. `onAdmitted`, which is where a trusted phone takes over from the connected one.
6. HELLO_ACK.

Trust is before the PIN because the PIN is a second factor on a phone the owner already said yes to, and the gate is before `onAdmitted` so a phone that has not proved itself can never end the connected phone's session. The gate knows nothing of sockets: it reads and writes through delegates and ends a silent wait through `giveUp`, which is why one copy serves every .NET laptop and a test can drive it frame by frame.

`PinStore` keeps two files beside the trust file: `security.txt` (the level and a salted PBKDF2-HMAC-SHA256 hash, never the PIN) and, at level 2, `pin-verified.txt` (the addresses that have entered it). Wrong answers are counted per address in memory only, and the lockout is 30 seconds after every fifth, doubling to an hour. [SECURITY.md](../SECURITY.md) says what that does and does not protect against. Two rules decide the failure direction: a settings file that is there and cannot be read, or holds anything Edgepad did not write, makes every phone need a PIN that cannot be checked, so it refuses them all until the owner uses **Reset PIN and forget phones…**; and a verified list that could not be cleared counts as empty, so level 2 asks again. A check that was hashing while the PIN or level changed is discarded by a generation counter, so a phone cannot be put on a list that was just cleared. Changing the PIN or the level clears the verified list.

**Holds.** A connected phone is a keyboard, so it could click through a dialog that changes security. Every owner dialog that does (Security, Reset PIN, Forget trusted phones) runs under `HoldOff()`, which hangs up on the phone and refuses new connections until the matching `Resume()`; holds are counted so two open dialogs cannot lift each other's. A connection that races a hold is refused rather than asked about over the owner's dialog.

**The withdrawn question.** The trust question is a window, and a session can end while it is open: a hold, a hang-up, quitting. The handshake takes the session's cancellation token (`ended`): it is checked before the question is put and after it is answered, and the window is closed when it fires. Both throw rather than answer no, so the owner is not recorded as having declined a phone they were never asked about, and a yes given after the session ended saves nothing. Before this, the question could stay up for 60 seconds over a dead session and the laptop then refused every phone after the hold ended.

## The Mac app

`macos/` is a Swift package with no Xcode project and no third-party dependency, split in two targets. `EdgepadCore` decides: the frame codec and stream reassembler, the key map, the dispatcher and its action table, the session and its handshake, the trust store, the log and the update check. It is pure Swift and unit-tested. `Edgepad` acts: the menu-bar app, IOBluetooth for RFCOMM, CGEvent for input, Core Audio for volume and microphone, and the display code. The core reaches the Mac only through the protocols in `Seams.swift` (an input sink, level controls, a brightness control, the display's rates, a transport), so the dispatcher and the handshake are tested with fakes and no radio, no permission and no display.

Before starting a session, the Mac checks `isPaired()` and requires `requestAuthentication()` to succeed. The socket Android requests is not a protection here, because an attacker chooses their own socket; these checks and the owner's yes are. The Mac hands over between phones by the same rules as Windows. The Mac does not gate on `getEncryptionMode()`: on macOS 27 that API returned zero while `bluetoothd` logged AES-CCM encryption and an encrypted RFCOMM security state for the same phone connection.

Everything runs on the main thread. IOBluetooth delivers its callbacks on the main run loop, so a `Session` is a state machine fed bytes as they arrive rather than a thread blocked in a read loop, and no session state needs a lock. The cost is that the owner's **Trust this phone?** question is modal and can take up to a minute, during which more bytes can arrive. `Session` keeps them in a pending buffer while the question is open and reads them after HELLO_ACK, in arrival order, so nothing is handled before the handshake finishes; a phone that sends more than 64 KiB while it waits is hung up on, though its question stays on screen until it is answered or times out. A connection that sends no HELLO within ten seconds is closed. Writes are asynchronous for the same reason reads are: a blocking write to a phone that had stopped reading would stop the one thread that injects input, serves the menu and accepts the reconnecting phone. Frames wait in an outbox of at most 64 KiB, far more than a healthy link ever queues, and a phone that lets that much pile up is treated as gone.

The app polls rather than subscribing to change notifications: twice a second the session reads volume, microphone and brightness and sends a STATE for any that moved. That is why a change made on the Mac itself reaches the phone within half a second and not instantly, and the cost is a read of all three twice a second for as long as a phone is live. A poll with no live session reads nothing.

Brightness goes through DisplayServices, a private macOS framework loaded at run time. It fails closed: where the framework is missing, or there is no built-in display, the dial has nothing to show and brightness up and down fall back to the brightness keys, which work on every Mac but cannot be measured.

The Mac maps keys by position, not by meaning. The wire carries Windows virtual-key codes, so Win is Command, Ctrl is Control and Alt is Option; the actions are macOS's default shortcuts, so a shortcut changed in System Settings changes what the gesture does. [PROTOCOL.md](PROTOCOL.md) lists them. Input only takes effect once the owner has granted input control in Device Control and Data Access (Accessibility before macOS 27); without it macOS silently discards what the app sends. The app needs both the Accessibility trust and permission to post events. If input still does nothing after the permission is granted, quitting Edgepad from the menu bar and opening it again is the fix.

Not built: now playing (and so media seeking), the on-screen level readout, and the virtual game controller. The Mac answers every request for the controller with `no-driver`, so the phone's gamepad falls back to keys exactly as it does on a Windows laptop without ViGEmBus. The Mac app was compiled and unit-tested in CI before its first run on a real Mac.

## Controls and the annotation overlay

The phone'"'"'s **Controls** screen is a deck of the keyboard, the gamepad, the macros and, when the laptop names the feature in TEXT 9, capture and annotate. A laptop that can do neither says nothing, and the phone shows nothing for it. Capture presses the OS's own screenshot or recording shortcut (see the action tables in [PROTOCOL.md](PROTOCOL.md)); there is no capture code in Edgepad.

Annotation is one idea implemented three times, because a transparent, click-through layer over the desktop is an OS window and nothing else. The stroke model is shared: `StrokeBoard` in the core (and its Swift twin) holds the strokes, the tools and the palette, and decides what a PEN frame means, so the three overlays can differ only in how they paint it. Each overlay shows only on the primary display, never takes focus, and is removed with its strokes when the phone says END, the session ends or the app quits.

| | Windows | macOS | Linux |
| --- | --- | --- | --- |
| Window | a WinForms form drawn with `UpdateLayeredWindow` for per-pixel alpha | a borderless `NSWindow` over the primary display | an Avalonia window, which is always an X11 one |
| Click-through, no focus | `WS_EX_TRANSPARENT`, `WS_EX_NOACTIVATE`, `WS_EX_TOOLWINDOW` | click-through, never key or main | an empty X input shape (`XShapeCombineRectangles`), never activated |
| Above other windows | topmost | above full-screen apps | `_NET_WM_STATE_ABOVE` |
| Offered when | always | always | only if the window is X11, a compositor is running and the server took the input shape; otherwise the phone gets `capture` only |
| Signature | PNG to the clipboard and `Pictures\Edgepad` | PNG and TIFF to the pasteboard and `~/Pictures/Edgepad` | PNG to the clipboard and the Pictures folder's `Edgepad` |

Linux is best effort and in testing. See **The Linux app** below and [LINUX.md](LINUX.md) for the cases that are unknown.

## The Linux app

`linux/` is a .NET 10 tray app, `Edgepad.Linux`, built self-contained as a single file for `linux-x64`. It uses the shared core for the protocol, handshake, trust, PIN, dispatch, macros and strokes, and supplies the rest:

- **Bluetooth.** `BluezProfile` exports an `org.bluez.Profile1` object on the system bus and registers it with `ProfileManager1.RegisterProfile` under the Edgepad service id (Tmds.DBus.Protocol). bluetoothd advertises the service, accepts the RFCOMM connection and hands the connected socket over in `NewConnection` as a file descriptor, which the session reads and writes as a stream. The profile is registered with `RequireAuthentication`, so only a paired device reaches it. The object sits on a bus any local process can reach, so it answers only calls whose sender is the bluetoothd that owns `org.bluez` and refuses the rest. `LinuxServer` registers again whenever that name changes hands, since a restarted bluetoothd has forgotten every profile, and retries a failed start every 30 seconds. One phone at a time, with the hand-off rules the Windows server has (`Admission`, written without a transport so it is tested).
- **Input.** Keys, pointer, scroll and typing go through `/dev/uinput` as a virtual keyboard and mouse, which works the same on Wayland and X11 and needs no root, only an ACL on the device (the `uaccess` udev rule `install.sh` writes). The gamepad is a second uinput device that copies a wired Xbox 360 pad. Typing presses keys for plain ASCII on a `us` layout and otherwise pastes through the clipboard. A KEY frame that would reach the kernel's magic SysRq (SysRq with Alt held) is dropped, since the phone's PrtSc maps to SysRq and Alt+SysRq+key reboots or kills.
- **Session watch.** A fast user switch hands the seat to another login session, and a uinput device outlives logind revoking this user's access, so the phone's keyboard would type into the other user's desktop. `SessionWatch` polls logind's `session/auto` twice a second and, while this session is not in front, calls `HoldOff()` (which hangs up and destroys the devices) and `Resume()` when it is back. Where logind cannot answer it assumes the session is in front, because failing closed would leave Edgepad doing nothing on a system with no logind and no fast user switch.
- **Controls.** Volume and microphone through `wpctl`, else `pactl`; brightness through logind's `SetBrightness` on a `/sys/class/backlight` device; media through MPRIS; lock through `loginctl`; macros through `xdg-open` or a program started without a shell. Values are polled twice a second, as on the Mac. The desktop shortcuts for task view, search, notifications and desktop switching are a table in `Platform/Desktop.cs` chosen from `XDG_CURRENT_DESKTOP` (GNOME and KDE); another desktop drops those actions. There is no refresh-rate dial: Linux has no shared way to switch display modes, so TEXT 4 is empty.
- **UI.** The tray icon, the trust question, the Security window and the PIN dialogs are Avalonia, written in C# with no XAML. The tray is a StatusNotifierItem, which GNOME does not show without the AppIndicator extension. Without a display the app still serves already-trusted phones and refuses any it would have had to ask about.
- **Files.** Settings in `$XDG_CONFIG_HOME/edgepad` (normally `~/.config/edgepad`), the single-instance lock in `$XDG_CACHE_HOME/edgepad`, the log in `~/.local/share/Edgepad`.

**Wayland and XWayland.** Input does not depend on the display server. Annotation does: Avalonia 12.1.4 has only an X11 backend on Linux, so on a Wayland session the overlay is an XWayland window, and whether GNOME's Mutter keeps an XWayland window above native Wayland ones and passes clicks through its input shape is not known. KDE is believed to honour both. Coordinates under fractional scaling, a second monitor and a PNG on the clipboard for Wayland apps are also unknown. The windows that ask for always-on-top may be ignored by a Wayland compositor, so the trust question also appears in the status line and the log. None of this has been seen on a real Linux laptop; [LINUX.md](LINUX.md) lists every case and how to check it.

## The phone's surface

`ControlSurface` is a single custom `View` that draws everything and receives every touch. There is no view hierarchy between the finger and the recogniser. A touch is classified where it starts: inside a corner's zone it belongs to that dial for its whole life, on a media piece or one of the three buttons along the top it is a button press, anywhere else it goes to `TrackpadRecognizer`. Geometry is computed once in `onSizeChanged`; nothing is allocated while drawing.

Two of those buttons open a screen — settings, and Controls (a deck of the keyboard, the gamepad, the macros and, when the laptop names the feature, capture, and annotate once it has also said its screen size). The third, the lock in the middle, walks the surface through `PadMode`: one tap hides the dials and the media and leaves the trackpad, a second inside the double-tap window locks the trackpad instead and puts them back, and any later tap returns the whole surface. The mode is gated where the surface already decides those things rather than beside them — `mediaShown()` and `dialAt()` both answer for it, and both are what `onDraw` and the hit test route through, so nothing is ever drawn without answering or answering without being drawn. Every mode change cancels the touch in flight, because arriving at a locked pad mid-drag would otherwise leave the left button held with no release to come. It is neither stored nor offered as a setting: a phone that came back up silently locked would read as broken.

Annotate is the phone as an absolute pen. `Letterbox` fits the laptop's aspect inside the panel and maps a touch to 0..65535 on each axis (clamped, so the margins are dead rather than stretching a circle), `AnnotateCanvas` sends a PEN frame for every sample including the historical ones, and `Strokes` is only the preview: the laptop owns the real ink, widths and undo. `MainActivity` owns the session, not the screen: ANNOTATE_BEGIN goes out when the screen is entered and ANNOTATE_END goes out exactly once however it is left (back, link loss, `onStop`, the rebuild for a rotation, which then begins a fresh session), tracked by one flag so no route sends it twice or sends it with no link. Sign mode is a second session on the laptop that shows nothing and takes only the pen, so switching either way clears the preview with it; the laptop's answer to SIGN_SAVE (TEXT 11) becomes a toast.

A stroke drawn on the trackpad is the one gesture that is not in the finger table. Press one finger, hold it still until it ticks, then draw without lifting; on lift the stroke goes to `Shapes`, a $1-style unistroke recogniser, and whatever it matched runs — a laptop action, a macro slot, or the surface's own focus or lock. That seam was free: a bare press and hold with no tap before it emitted nothing at all on this pad. The recogniser takes the shape sink as null when nothing is bound, so a phone whose owner has drawn no shapes keeps exactly the old behaviour rather than swallowing a third of a second of pointer movement on every press.

`Perimeter` models the screen's edge as one clockwise path, a rounded rectangle whose corner radius is the display's own (`WindowInsets.getRoundedCorner`), so a ruler bends round a corner instead of being clipped by it. A dial's finger position is projected onto that path and its movement measured along it.

`TrackpadRecognizer`, `Dial`, `Shapes`, `PadMode`, `PadAxis` and `GamepadLibrary` are pure Kotlin with no Android types, which is what lets the gesture table, the shape maths, the pad's transitions, the stick's arithmetic and the layout library's rules all run as JVM unit tests. `PadAxis` is there deliberately: until 3.0.0 nothing covered touch to controller output at all, because it sat unreachable inside a `View`'s touch handler. Inside the layout, `Binding.fits` is the single answer to which bindings suit a kind of control: the picker builds its list from it and the store validates against it, so the editor can never offer a pairing the store would refuse. `InputNames` holds what each of them is called on screen, in Kotlin rather than in `strings.xml`, because a legend moulded into a keycap is the same characters whatever language the phone is set to.

## Settings and state

Settings live in one `SharedPreferences` file; the theme is applied as the system's own per-app night mode, and the choice itself (System, Dark or Light) is kept as a preference, because the platform has no public way to read the app's night mode back. Dial positions and the gesture map are stored by enum name, so a renumbering cannot silently remap them. Media-piece positions are fractions of the surface's width and height, so a layout made in portrait keeps its shape in landscape. The drawn shapes are text in the same file, and a set that fails to decode reads as no shapes at all rather than as the ones that happened to parse — a hub row claiming four shapes over a trackpad that recognises none would send the owner looking in the wrong place.

The gamepad's layouts are a library rather than one saved arrangement, which is what per-game needs. `GamepadStore` is a thin wrapper over `GamepadLibrary`, and the library is two strings: the saved layouts, and the name of the one in play. The built-in presets are never stored — a saved layout of the same name shadows one instead — so the layout Edgepad ships can always be got back, can never be renamed away, and the list is never empty. A name that collides costs a number and never a layout: overwriting would throw away an arrangement nothing can recover, and refusing needs somewhere to print an error that a popup over a full-screen canvas does not have. A layout saved by 2.x is refused rather than migrated, and the first preset takes its place, because a 2.x layout has no controller bindings in it to migrate and pretending otherwise would be a lie.

The Orientation setting holds every screen except the keyboard, the gamepad and the gamepad layout editor, and those three are always sideways. The media-layout editor is held with the rest on purpose: a media layout has been stored per orientation since 2.3.0, so a phone turned mid-edit would quietly begin changing the other one.

## What the tests cover

`protocol/frames.txt` and `protocol/actions.txt` are golden fixtures, plain text, read by every test suite at run time rather than copied into any. `frames.txt` lists every frame type as literal hex bytes next to the fields they mean; `FrameFixtureTest` on the phone and `FrameFixtureTests` on the laptop each parse the same file, encode the fields and assert on the exact bytes, then decode the bytes and assert on the exact fields. `actions.txt` does the same for the action and control ids, checked by `IdsFixtureTest` / `IdsFixtureTests`. Because one file drives assertions in three codebases (the Kotlin codec, the C# codec the Windows and Linux apps share, and the Swift one), a change to one codec without the matching change in the others fails that side's test immediately — the fixture is what stops the apps from drifting apart, not code review. A protocol change therefore always touches a fixture file and all three codecs in the same commit (see CONTRIBUTING.md).

The Mac suite (`macos/Tests/EdgepadCoreTests`) reads the same two fixtures, so three codecs are now held to one file. It also covers the stream reassembler, the key map, the dispatcher's drop paths and action table, the trust store, the handshake and its refusals, and the update-version parsing. Nothing that touches Bluetooth, CGEvent, Core Audio or the display is tested.

Above that fixture layer, the Android suite (`android/app/src/test`) covers the gesture recogniser and the whole finger table, natural scrolling, the shape recogniser and the text a set of shapes is stored as, the pad's mode transitions, the stick's dead zone and magnitude scaling, the gamepad layout's encoding and the library's rules (name collisions, deletion, reset, a 2.x layout refused), the dials (arming, slop, snapping, steppers, haptic notches), the corner/perimeter geometry, coalescing, and the laptop-state model — all pure Kotlin, no Android platform types, so it runs as a plain JVM unit test with no emulator. The shared core's suite (`shared/Edgepad.Core.Tests`) covers the codec against the fixtures, the dispatcher's routing and drop paths, the handshake and its refusals and races, trust-on-first-use, the PIN store and gate (lockout schedule, the verified list, the unreadable-file cases) and the stroke model, and runs on Linux in CI as well as on Windows, which is what catches a path-case, file-lock or line-ending assumption that Windows forgave. The Linux suite (`linux/tests/Edgepad.Linux.Tests`) covers the hand-off rules, the uinput events and the SysRq filter, the key, typing and desktop-shortcut tables, the virtual pad's report, the session watch, the audio, backlight, MPRIS and macro-launcher logic, the PIN entry and trust prompt, and the annotation geometry. The Windows suite (`windows/tests/Edgepad.Tests`) covers what only the Windows app does, such as input batching, the media-session title mapping, and what a laptop with no controller driver answers — a `VirtualPad` handed a client that throws what an absent ViGEmBus throws, so the assertion holds on a build machine and on a desk that does have the driver, and neither ends up with a controller plugged into it. The paths that need the driver, a pad that actually plugs in and the attach-failed answer, have no test: a fake client cannot produce a real Xbox360 target. No suite sends real input, opens a real Bluetooth socket, or touches a device; that is only exercised by running a laptop app and the phone against each other by hand (see CONTRIBUTING.md). Nothing in the Linux suite can reach BlueZ, uinput or an X server.

Counted from the source on 2026-10-24 as test declarations, with a parameterised test counted once however many cases it runs: shared core 159 (141 `[Fact]`, 18 `[Theory]`), Linux 136 (104, 32), Windows 81 (67, 14), Android 249 (`@Test`), Mac 299 (`func test…`). They move with every change, so treat them as a snapshot and not a promise; the CI result is the authority.

## Build and release

One script, `scripts/check.ps1`, is the quality gate for every half: format, lint (warnings are errors on every side), build, test. `-Only android|core|windows|linux|macos` runs one gate: `core` is the shared library and its tests, `windows` and `linux` build the laptop app and its tests (a laptop app's gate builds the core as a project reference, so it covers it too). The Mac half (`swift format lint --strict`, `swift build` with warnings as errors, `swift test`) runs only on a Mac; a plain run on Windows or Linux skips it. CI runs the script in its non-mutating `-Ci` mode on every push and pull request in six jobs: `android` (the gate, then a debug APK), `core` (the shared core on Ubuntu, where the Linux app will run it), `linux` (the gate, then a self-contained single-file publish for `linux-x64` and the `tar.gz`), `windows` (the gate, then the self-contained exe), `macos` (the Mac gate, then the ad hoc signed app) and `lockfiles` (below). A version tag runs the same gates and publishes a GitHub Release with a signed APK, the exe, `Edgepad-<version>-mac.zip` and `Edgepad-<version>-linux-x64.tar.gz`, each named for its version and listed in `SHA256SUMS.txt`. The tarball is built by `linux/packaging/pack.sh` from the publish folder, owned by root inside the archive so `sudo tar x` cannot leave an installer owned by the CI runner's uid, and byte-for-byte reproducible for one commit; it holds the binary, `install.sh` (which copies files and loads the `uinput` module and downloads nothing), the udev rule, the modules-load entry, the desktop entry and the icon. The Linux native libraries (SkiaSharp and HarfBuzz) are inside the single file and unpack to `~/.net` on first start.

**Lock files.** Every .NET project restores with `RestorePackagesWithLockFile`, and CI (`CI=true`) restores in locked mode (`Directory.Build.props`), so a package that changed under the same version, or a lock file nobody regenerated, fails the build instead of shipping. A project that names `RuntimeIdentifiers` gets those runtimes' packages in its lock file, which is why the core lists `win-x64;linux-x64` and the apps their own. No SDK is needed on the contributor's machine: the `lockfiles` job runs `dotnet restore --force-evaluate` with locked mode switched off for the six projects and uploads the `packages.lock.json` files as the `edgepad-lockfiles` artifact; `gh run download` it, commit what it holds, and push again. CONTRIBUTING.md has the steps. The zip holds `Edgepad.app`, wrapped from the Swift Package Manager binary by `macos/bundle.sh`, universal for Apple Silicon and Intel, ad hoc signed and not notarised; it is listed in `SHA256SUMS.txt` and the provenance attestation. The APK is built unsigned and signed in a job of its own, which waits for the owner's approval; the signing key exists only in that job's `release` environment secrets and on the machine that created it; `scripts/new-signing-key.ps1` makes it once and never prints it.

The laptop app is a per-user tray app rather than a Windows service on purpose: services run in session 0 and can neither inject input into the desktop nor reach the user's audio session. It is single-instance, and a newer copy asks the running one to quit and waits for the lock, so an update takes over cleanly. The Mac app is a menu-bar app, and the Linux app a per-user tray app with a lock on `~/.cache/edgepad/lock`, for the same reason: they need the user's session to inject input and reach audio. Because its signature is ad hoc, macOS treats each version as a different app and the Device Control permission has to be granted again after an update.
