# Security

Edgepad lets a phone drive a laptop, so its boundaries matter. This is what they are and how to report a hole in one.

## The model

- **Only paired devices can connect.** Windows binds its Bluetooth socket with encryption and authentication. The Mac app checks that the device is paired and requires `IOBluetoothDevice.requestAuthentication()` to succeed before starting a session: an address alone is not proof of identity. The socket Android asks for (`createRfcommSocketToServiceRecord`) is not a protection, because an attacker chooses their own socket. The laptop-side gates are that the device is paired, that its link authenticates (on a Mac `requestAuthentication()` succeeds, and the log says how long it took; on Windows, the socket's `BluetoothEncryptionWithAuthentication` protection level), and the owner's yes below. On macOS, encryption is provided by the Bluetooth stack; the app does not independently verify it. The old `getEncryptionMode()` check was removed after macOS 27 reported zero for an RFCOMM connection that `bluetoothd` confirmed was AES-CCM encrypted. Over the optional Wi-Fi and USB link (Windows, Linux and the Mac; off until the owner turns it on) the gate is different: the phone shows a six-digit code, the owner types it on the laptop once, and after that the phone reconnects without asking. The details of that link are in the network section of [docs/PROTOCOL.md](docs/PROTOCOL.md); this document does not restate them, and the phone's half has not been tried on real devices yet.
- **Only phones you trust, and you choose each one.** Any phone paired with the laptop is asked about once: when it completes the handshake, the tray asks **Trust this phone?**; only **Trust** remembers it by address, and no answer within 60 seconds counts as **Don't trust**. Each yes is added to the same list, one address per line, so you can trust several phones. **Every phone you trust has full keyboard-level control of the laptop, so trust only your own.** A trusted phone that is connected can answer the question about another phone with its keyboard, which gives it nothing it did not already have. You undo trust with **Forget trusted phones** in the tray menu (the menu-bar menu on a Mac), which asks before it forgets and forgets every trusted phone; there is no way to forget one. Choosing it hangs up on the connected phone and takes no connection while the confirmation is open, since a connected phone is a keyboard and could answer the confirmation itself; if you cancel, the phone reconnects by itself as long as its own retries have not run out. Forgetting then refuses every connection for the next 30 seconds, so the phone's automatic reconnect cannot raise the question again under the click that just dismissed it, and a Forget clicked while a question is open wins over a yes given afterwards. A phone you answer **Don't trust** to, or leave unanswered, is not asked about again for 30 seconds, and a connection that arrives while the question is open is refused without disturbing the phone being asked about. On a Mac the question's **Trust** button stays disabled for its first 2 seconds, and **Don't Trust** is the default on both. The Mac's question shows the phone's Bluetooth name in quotes, stripped to plain characters and cut to 40, because the phone chooses that name; the address beside it is what gets trusted. The Windows question shows the address alone.
- **An optional PIN, and what it is for.** The laptop's security level (Security… in the tray, or the Mac's menu bar) is 1 by default: trust only, as above. Level 2 also asks each phone for a six-digit PIN once, and level 3 on every connection; the PIN is asked after the trust question and before the phone is admitted, so a phone that has not given it can never displace the connected one. The laptop stores a salted PBKDF2-HMAC-SHA256 hash of it (600,000 iterations, a 16-byte random salt, compared in constant time), never the PIN. The phone never stores it, its keypad is the app's own so no keyboard app sees the digits, and its screen cannot be captured. No log line, status text or debug print on any platform contains the digits.
- **The PIN is a lock-out, not a secret that survives theft of the file.** Read this before relying on it. Six digits are 10^6 values. PBKDF2 with 600,000 iterations slows each guess, but it cannot make a million-value space expensive: someone who copies `security.txt` can try all one million values offline, with no lock-out, paying only the hash time per guess times a million, which is a cost and not a barrier. The hash does not stop that and is not meant to. What actually stops guessing is, first, the online lock-out: every fifth wrong answer from a phone's address locks it out for 30 seconds, doubling with each further five, up to an hour, and a locked-out phone is turned away before the owner is asked anything; the counters are in memory, so quitting the laptop app clears them (and doing that needs the owner's desktop, which is what the PIN stands in for). Second, the file lives in the owner's own profile: the per-user `%APPDATA%` folder on Windows, and on a Mac and Linux a folder created 0700 with files written 0600. Anyone who can read your profile can already read your files and run programs as you, which the PIN was never going to prevent. A phone that is trusted and has the PIN is still a keyboard.
- **A forgotten PIN resets only on the laptop, and forgets every trusted phone.** **Reset PIN and forget phones…** deletes the PIN, goes back to level 1 and forgets every trusted phone, after asking, in that order, so the way back in is the owner's own yes on this laptop. There is no reset from the phone. Changing the PIN or the level, and **Forget trusted phones**, also clear the list of phones that have entered the PIN, so each enters it again. A settings file that cannot be read, or holds anything Edgepad did not write, refuses every phone until the PIN is reset; it never lets one in.
- **A connected phone cannot answer security questions, because the laptop hangs up first.** Every dialog that changes security (the Security window, Reset PIN, Forget) hangs up on the phone and takes no connection while it is open, since a connected phone is a keyboard. The trust question is withdrawn too when anything ends the session behind it, a hold or a hang-up included, without recording a refusal; a yes that arrives after the session ended saves nothing.
- **On Linux only bluetoothd may hand over a connection.** The app exports its Bluetooth profile on the system bus, where any local process can call it, and answers only calls whose sender is the bluetoothd that owns `org.bluez`. It registers with `RequireAuthentication`, so only a paired device is connected, and the trust question and PIN follow as on the other laptops.
- **On Linux input goes through `/dev/uinput`, and your user needs access to it.** `install.sh` installs a udev rule that tags the device with `uaccess`, which gives access to the user logged in at the seat and nobody else, instead of making `/dev/uinput` readable by a group or by everyone. A trusted phone's keyboard therefore exists only while your own session is in front: on a fast user switch logind revokes your access but a uinput device outlives it, so Edgepad watches the session and hangs up on the phone, destroying its devices, until you are back. If logind cannot be asked (no systemd or elogind) it assumes the session is in front, because there is no fast user switch to report on such a system. The Alt key plus SysRq is never sent: Alt+SysRq+key is the kernel's magic SysRq (reboot, sync, kill), and the phone's PrtSc maps to SysRq.
- **One phone drives the laptop at a time, and only an admitted phone can displace it.** A trusted phone that connects takes over from the connected one, but only after its handshake and trust check succeed, so an untrusted phone that connects cannot drop the connected one. The phone that was replaced is refused for 30 seconds, which outlasts its automatic retries, so two trusted phones do not take the laptop back and forth; after that it can reconnect with Retry.
- **A paired phone is a trusted input device.** It sends pointer movement, buttons, scroll, zoom, key codes and text to type. The keyboard screen sends raw Windows virtual-key codes (`KEY`) and arbitrary characters (`TEXT` kind 3), which the laptop injects directly, so anything that could be done at the laptop's own keyboard can be done from the phone. The action and control ids are a fixed, laptop-owned table, which keeps the two halves independently versionable and lets an unknown id be dropped rather than misexecuted — it is **not** a containment boundary and should not be read as one. The trust boundary is the pairing plus trust-on-first-use above.
- **Windows keeps its own line.** Injected input never reaches an elevated window, a UAC prompt or the lock screen; the laptop counts those refusals.
- **macOS keeps its own line too.** On a Mac, input the app injects takes effect only once you have granted it input control (Accessibility, named Device Control and Data Access from macOS 27) and event posting; until then macOS discards it.
- **Nothing you do leaves the two devices.** No server, no account, no telemetry. The one thing the phone app says to the internet is a daily question to GitHub, "which release is newest?", and the download of that release when you ask for it. Neither carries anything about the phone, and the daily question can be switched off under System settings. Android installs the download only if it is signed with the same key as the app it replaces. The laptop app asks GitHub the same question when it starts and once a day after, downloads nothing itself, and has no switch for it. The laptop writes a local log of connections and errors and nothing else (on a Mac, `~/Library/Logs/Edgepad/edgepad.log`; on Linux, `~/.local/share/Edgepad/edgepad.log`).
- **The clipboard is shared with one laptop, on both devices' say-so.** While sharing is on, text and images copied on the laptop you are controlling are sent to the phone, so anything you copy there, a password included, reaches the phone unless a password manager marks it as sensitive, in which case it is never sent. Android lets Edgepad read the phone's clipboard only while Edgepad is on screen, so a copy from the phone is sent when you return to Edgepad, never in the background. Only the laptop you are controlling shares, and the phone and each laptop have a switch.
- **No secrets in the repository.** The APK signing key exists only in the secrets of a GitHub Actions environment, which releases nothing without the maintainer's approval, and on the machine that created it.

## Known limits

- The trusted phones' Bluetooth addresses are stored in plain text in `trusted-phone.txt`, one per line: under `%APPDATA%\Edgepad` on Windows, in `~/Library/Application Support/Edgepad` on a Mac and in `$XDG_CONFIG_HOME/edgepad` (normally `~/.config/edgepad`) on Linux. On a Mac and Linux the folder is created 0700 and the file written 0600; on Windows the per-user `%APPDATA%` folder is already private. Anyone who can write that file can change which phones are trusted; that person can already run programs as you. `security.txt` and `pin-verified.txt`, which hold the PIN's hash and the phones that have entered it, sit beside it.
- The PIN is six digits and its hash can be attacked offline by anyone who can copy `security.txt`; only the online lock-out and the file's permissions protect it (see The model). The lock-out counters are in memory and restart with the app.
- The Linux app has not been seen working on a Linux laptop. Its Bluetooth profile, uinput access, tray, trust question and annotate layer are written from documentation and CI-tested only, and [docs/LINUX.md](docs/LINUX.md) lists each unknown. On a Wayland session annotate runs as an XWayland window, whether it stays above native windows and passes clicks through is unknown, and it is offered only when it can work. The Linux download carries SkiaSharp and HarfBuzz native libraries inside the single file; they are not updated except by a new Edgepad release.
- An older Edgepad reads a trust file that lists two phones as one unknown address, so going back to an older release after trusting a second phone refuses every phone until you choose **Forget trusted phones**.
- The Mac app is ad hoc signed and not notarised, because the project has no Apple Developer ID, so macOS refuses it on first launch until you choose Open Anyway in System Settings. Check the zip against `SHA256SUMS.txt` and with `gh attestation verify Edgepad-<version>-mac.zip --repo akshit-bansal11/edgepad`.
- The Mac app reads and sets brightness through a private macOS framework, DisplayServices, loaded at run time. It is not a documented interface and may change under it.
- The Mac app's first run on real hardware was a contributor's, on macOS 27, reported with the fix for its encryption check. Beyond the connection that fix needed, its input injection, audio and display code is compiled and unit-tested in CI but has not been reported working on a Mac.
- **Forget trusted phones** needs to delete or empty the file that names the phones. If it can do neither, it says so and refuses every phone while it stays running, but the file still names them, and they are trusted again the next time the app starts unless you remove the file.
- The laptop app is not code-signed. SmartScreen warns on first run. Verify the download came from this repository's Releases page; releases after 3.1.1 can also be checked against their `SHA256SUMS.txt` and with `gh attestation verify`.
- Text typed from the phone goes wherever the laptop's focus is, like a keyboard would.
- Because the phone can press keys and type, it can reach anything a keyboard can — Win+R and a typed line is already arbitrary execution. Whoever holds a trusted phone has the laptop's keyboard. Use **Forget trusted phones** if you lose one; you then trust the others again.

## Reporting

Open a [security advisory](https://github.com/akshit-bansal11/edgepad/security/advisories/new) on GitHub; it reaches the maintainer privately. Please do not open a public issue for something exploitable. Expect an acknowledgement within a week.
