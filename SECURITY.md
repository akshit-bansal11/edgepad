# Security

Edgepad lets a phone drive a laptop, so its boundaries matter. This is what they are and how to report a hole in one.

## The model

- **Only paired devices can connect.** Windows binds its Bluetooth socket with encryption and authentication. The Mac app checks that the device is paired and requires `IOBluetoothDevice.requestAuthentication()` to succeed before starting a session: an address alone is not proof of identity. The socket Android asks for (`createRfcommSocketToServiceRecord`) is not a protection, because an attacker chooses their own socket. The laptop-side gates are that the device is paired, that its link authenticates (on a Mac `requestAuthentication()` succeeds, and the log says how long it took; on Windows, the socket's `BluetoothEncryptionWithAuthentication` protection level), and the owner's yes below. On macOS, encryption is provided by the Bluetooth stack; the app does not independently verify it. The old `getEncryptionMode()` check was removed after macOS 27 reported zero for an RFCOMM connection that `bluetoothd` confirmed was AES-CCM encrypted.
- **Only phones you trust, and you choose each one.** Any phone paired with the laptop is asked about once: when it completes the handshake, the tray asks **Trust this phone?**; only **Trust** remembers it by address, and no answer within 60 seconds counts as **Don't trust**. Each yes is added to the same list, one address per line, so you can trust several phones. **Every phone you trust has full keyboard-level control of the laptop, so trust only your own.** A trusted phone that is connected can answer the question about another phone with its keyboard, which gives it nothing it did not already have. You undo trust with **Forget trusted phones** in the tray menu (the menu-bar menu on a Mac), which asks before it forgets and forgets every trusted phone; there is no way to forget one. Choosing it hangs up on the connected phone and takes no connection while the confirmation is open, since a connected phone is a keyboard and could answer the confirmation itself; if you cancel, the phone reconnects by itself as long as its own retries have not run out. Forgetting then refuses every connection for the next 30 seconds, so the phone's automatic reconnect cannot raise the question again under the click that just dismissed it, and a Forget clicked while a question is open wins over a yes given afterwards. A phone you answer **Don't trust** to, or leave unanswered, is not asked about again for 30 seconds, and a connection that arrives while the question is open is refused without disturbing the phone being asked about. On a Mac the question's **Trust** button stays disabled for its first 2 seconds, and **Don't Trust** is the default on both. The Mac's question shows the phone's Bluetooth name in quotes, stripped to plain characters and cut to 40, because the phone chooses that name; the address beside it is what gets trusted. The Windows question shows the address alone.
- **One phone drives the laptop at a time, and only an admitted phone can displace it.** A trusted phone that connects takes over from the connected one, but only after its handshake and trust check succeed, so an untrusted phone that connects cannot drop the connected one. The phone that was replaced is refused for 30 seconds, which outlasts its automatic retries, so two trusted phones do not take the laptop back and forth; after that it can reconnect with Retry.
- **A paired phone is a trusted input device.** It sends pointer movement, buttons, scroll, zoom, key codes and text to type. The keyboard screen sends raw Windows virtual-key codes (`KEY`) and arbitrary characters (`TEXT` kind 3), which the laptop injects directly, so anything that could be done at the laptop's own keyboard can be done from the phone. The action and control ids are a fixed, laptop-owned table, which keeps the two halves independently versionable and lets an unknown id be dropped rather than misexecuted — it is **not** a containment boundary and should not be read as one. The trust boundary is the pairing plus trust-on-first-use above.
- **Windows keeps its own line.** Injected input never reaches an elevated window, a UAC prompt or the lock screen; the laptop counts those refusals.
- **macOS keeps its own line too.** On a Mac, input the app injects takes effect only once you have granted it input control (Accessibility, named Device Control and Data Access from macOS 27) and event posting; until then macOS discards it.
- **Nothing you do leaves the two devices.** No server, no account, no telemetry. The one thing the phone app says to the internet is a daily question to GitHub, "which release is newest?", and the download of that release when you ask for it. Neither carries anything about the phone, and the daily question can be switched off under Settings › Help. Android installs the download only if it is signed with the same key as the app it replaces. The laptop app asks GitHub the same question when it starts and once a day after, downloads nothing itself, and has no switch for it. The laptop writes a local log of connections and errors and nothing else (on a Mac, `~/Library/Logs/Edgepad/edgepad.log`).
- **No secrets in the repository.** The APK signing key exists only in the secrets of a GitHub Actions environment, which releases nothing without the maintainer's approval, and on the machine that created it.

## Known limits

- The trusted phones' Bluetooth addresses are stored in plain text in `trusted-phone.txt` under `%APPDATA%\Edgepad`, one per line. Anyone who can write that file can change which phones are trusted; that person can already run programs as you.
- On a Mac the trusted phones' addresses are stored in plain text in `~/Library/Application Support/Edgepad/trusted-phone.txt`, created readable by its owner only. The same reasoning applies.
- An older Edgepad reads a trust file that lists two phones as one unknown address, so going back to an older release after trusting a second phone refuses every phone until you choose **Forget trusted phones**.
- The Mac app is ad hoc signed and not notarised, because the project has no Apple Developer ID, so macOS refuses it on first launch until you choose Open Anyway in System Settings. Check the zip against `SHA256SUMS.txt` and with `gh attestation verify Edgepad-<version>-mac.zip --repo akshit-bansal11/edgepad`.
- The Mac app reads and sets brightness through a private macOS framework, DisplayServices, loaded at run time. It is not a documented interface and may change under it.
- The Mac app's first run on real hardware was a contributor's, on macOS 27, reported with the fix for its encryption check. Beyond the connection that fix needed, its input injection, audio and display code is compiled and unit-tested in CI but has not been reported working on a Mac.
- **Forget trusted phones** needs to delete or empty the file that names the phones. If it can do neither, it says so and refuses every phone while it stays running, but the file still names them, and they are trusted again the next time the app starts unless you remove the file.
- The laptop app is not code-signed. SmartScreen warns on first run. Verify the download came from this repository's Releases page; releases after 3.1.1 can also be checked against their `SHA256SUMS.txt` and with `gh attestation verify`.
- Text typed from the phone goes wherever the laptop's focus is, like a keyboard would.
- Because the phone can press keys and type, it can reach anything a keyboard can — Win+R and a typed line is already arbitrary execution. Whoever holds a trusted phone has the laptop's keyboard. Use **Forget trusted phones** if you lose one; you then trust the others again.

## Reporting

Open a [security advisory](https://github.com/akshit-bansal11/edgepad/security/advisories/new) on GitHub; it reaches the maintainer privately. Please do not open a public issue for something exploitable. Expect an acknowledgement within a week.
